# Trofeo Vision 11.3 LCD — кастомный драйвер и монитор

## Контекст проекта

Thermalright Trofeo Vision 11.3 LCD BLACK — USB-панель для ПК-корпуса.
Родной софт (TRCC) есть только под Windows. Протокол реверс-инженерен
по USB-дампам TRCC v2 (Wireshark + USBPcap) и полностью воспроизведён
в `monitor.py`. Скрипт работает: рендерит системные метрики через
Pillow и шлёт кадры на панель через PyUSB. Проверено на macOS (Mac
mini), целевая среда — Linux/Proxmox.

## Железо

- USB ID: `0416:5408`, product string "USBDISPLAY", bcdDevice 1.18
- Один интерфейс (class 0xff vendor), два bulk endpoint:
  EP_OUT `0x09`, EP_IN `0x81`, maxpkt 512
- Разрешение буфера: **1920x440** (маркетингово «400-строчная» — реально 440)
- Панель раз в ~2 секунды шлёт heartbeat-пакет `03 ff 00 ... 02 ...`
  в EP_IN; его надо вычитывать (drain), иначе IN-буфер переполняется
- Сторожевой таймер: без нового кадра ~1-2 секунды панель возвращает
  заводской логотип. Интервал обновления держать ~1с
- При получении некорректного потока прошивка виснет и перестаёт
  подтверждать пакеты (write timeout, обычно на блоке 1); лечится
  только передёргиванием кабеля, `dev.reset()` не помогает

## Протокол кадра (доказан побайтовым сравнением с дампом TRCC)

Кадр = **524 блока по 512 байт**, отправляется bulk-записями
65 x 4096 (по 8 блоков) + 1 x 2048 (4 блока). Итого 268288 байт.

Каждый 512-байтный блок:

```
[0:2]   01 ff                    магия
[2:4]   field, u16 LE            функция длины JPEG (см. ниже)
[4:11]  03 00 f0 01 01 0a 02     константа
[11:15] номер блока, u32 LE      0..523
[15]    00
[16:]   496 байт данных JPEG
```

Полезная нагрузка кадра: 524 * 496 = 259904 байта.

**JPEG:** baseline (не progressive), 4:2:0, 1920x440. Кодируется PIL:
`img.save(buf, "JPEG", quality=85, subsampling=2)`.

**Паддинг:** JPEG добивается COM-сегментами (FF FE) перед FF D9 до
ровно **258507 байт** (длина эталонного кадра TRCC). Тогда
field = **0xF1CB** — пара «длина+поле», подтверждённая реплеем
реального кадра TRCC. Хвост payload после JPEG добивается нулями.

**Формула поля** (восстановлена по 19 кадрам из двух независимых
дампов, 19/19 совпадений; валидированный диапазон «грязных» длин
265420..266658):

```python
def frame_field(clean_len):
    b = max(0, (clean_len - 1) // 496)      # блок последнего байта
    non8 = b - b // 8
    c = clean_len + 16 * non8               # «грязная» длина (с заголовками)
    return (c - 16 * (c // 512) - 195600) & 0xFFFF
```

Поле зависит ТОЛЬКО от длины JPEG, не от содержимого (доказано
мутационным тестом: инвертированный байт в entropy-данных панель
показывает с артефактом, не виснет). Вне валидированного диапазона
формула — экстраполяция, поэтому по умолчанию используется паддинг
до 258507 и константа 0xF1CB.

Handshake НЕ нужен и вреден: любой «лишний» пакет сбивает выравнивание
потока. Панель не отвечает на команды, heartbeat идёт по таймеру.

## Что уже есть: monitor.py

- `render_frame()` — Pillow-рендер 1920x440: шапка (hostname, uptime,
  load average, часы/дата) + 4 панели: CPU (общий %, температура,
  до 16 ядер в 2 колонки), MEMORY (+swap), DISK /, NETWORK
  (скорости + суммарный трафик). Вся геометрия из констант
  (MARGIN/GAP/PANEL_W/COL), шрифты с фолбэками Linux+macOS
- `build_chunks(jpeg, field)` — сборка кадра по блочному протоколу
- `send_image(dev, img)` — рендер -> JPEG -> COM-паддинг -> отправка
- `open_device()` — поиск (в т.ч. по запасным ID), detach kernel
  driver, claim, автодетект bulk endpoints
- `recover()` / `drain_in()` — снятие halt, вычитка heartbeat
- Основной цикл: кадр в секунду, при ошибке recover + переподключение
- CLI: `--preview out.png` (кадр без USB), `--once`, `--interval`,
  `--replay file.jpg` (кадры из дампа, сам чистит вкраплённые
  заголовки), `--mutate N`, `--inspect file.jpg` (разбор JPEG-маркеров
  без PIL-декода), `--watchdog`, `--reset`, `--list`, `--info`,
  `--no-pad` (чистая формула без паддинга — экспериментально),
  `--field 0x...`; диагностические `--probe`, `--try-formats`, `--zlp`
  устарели (артефакты реверса, можно удалить при рефакторинге)
- Есть также `parse_trcc_capture.py` — разбор .pcapng через tshark
  (`--decode --dump-jpeg`, `--solve`); нужен только для дальнейшего
  реверса, в рантайме не участвует

Зависимости: `pyusb`, `pillow`, `psutil`; libusb в системе
(macOS: `brew install libusb`). На Linux для запуска без root нужно
udev-правило на 0416:5408.

## Следующая задача: бек + фронт для контента панели

Цель: простой backend + frontend, чтобы конфигурировать, ЧТО панель
показывает, вместо захардкоженного макета в render_frame().

**Статус: бекенд готов** (см. `backend/`, описание API в
`backend/README.md`). FastAPI-демон: фоновый поток владеет USB и шлёт
кадры, конфиг в `backend/data/config.json` (pydantic-валидация),
виджеты cpu/memory/disk/network/clock/image/calendar/worldclock/weather
(погода - Open-Meteo без ключа, кэш в app/weather.py), панелей 1-4, предпросмотр
PNG, загрузка картинок, dev-режим `PANEL_NO_USB=1`. На macOS
для USB может понадобиться sudo; на Linux - udev-правило (есть в README).

**Протокол и USB вынесены в отдельный pip-пакет `trofeo-lcd/`**
(TrofeoPanel.open()/send_image(), frame_field, pad_jpeg_com,
build_chunks, encode_frame). Побайтово сверен с monitor.py - формулы
не менять. Ставится `pip install -e trofeo-lcd` (install.sh делает
сам), бекенд импортирует `from trofeo_lcd import ...`. Библиотеку
можно использовать в других проектах, README пакета с примерами.

**Фронтенд готов** (`frontend/`, Vite + React 19): 4 слота, в каждом
выбор виджета («нет» = слот пуст, панелей может быть 1-4) и его
настройки по схемам из /api/widgets; живой предпросмотр через
POST /api/preview.png с дебаунсом; статус панели; кнопка сохранения.
Dev: `npm run dev` (фронт на :3333, прокси /api на :8888). Прод: `npm run build`,
собранный `frontend/dist` бекенд раздаёт сам со своего порта -
деплой одним процессом.

**Паритет с flutter-версией и Pi-деплой (2026-10)**: бекенд
локализован EN/UK (config.language, l10n.py, рендер без русского,
каталог /api/widgets отдаёт title + title_uk), календарь догнан до
flutter: STATUS:CANCELLED, RECURRENCE-ID, Windows TZID, skip_today
(таймзоны у python были корректны изначально: aware-арифметика +
astimezone на вхождение). Веб-конфигуратор EN/UK с переключателем.
ConfigStore пишет config.json.bak при каждом сохранении. Целевой
хост панели - Raspberry Pi 4 1GB (64-bit RPi OS), «сервер»
синхронизации = сама Pi (её HTTP API), flutter-приложение имеет
Remote-режим поверх этого API и шлёт метрики своего компьютера
(POST /api/metrics, TTL 5с): панель у Pi показывает cpu/memory/disk/
network Мака; при пропаже потока (>10с) виджеты показывают "No data"
(метрики Pi не прыгают); `metrics_fallback_sec` в конфиге включает
откат на метрики хоста через N секунд, по умолчанию 0 = никогда.

**Упаковка готова**: `./install.sh` (venv + зависимости + сборка
фронта), `./run.sh` (запуск, env: PORT, PANEL_NO_USB=1),
`deploy/trofeo-panel.service` (systemd), `deploy/99-trofeo.rules`
(udev), `Dockerfile` (multi-stage, для Linux с `-v /dev/bus/usb`).

Пожелания к архитектуре (обсуждаемо):

- **Backend (Python, FastAPI)** — стек пользователя. Демон владеет
  USB-устройством и циклом отправки; HTTP API для конфигурации
  (какие виджеты, их порядок/настройки) и, возможно, загрузки
  своих картинок/тем. Один процесс должен владеть устройством —
  веб-сервер и цикл отправки держать в одном процессе (фоновая
  задача) либо разделить через очередь
- **Frontend (React)** — стек пользователя. Конфигуратор макета:
  выбор виджетов (CPU/RAM/диск/сеть/часы/погода/своя картинка),
  предпросмотр кадра (тот же рендер, отдавать PNG с бекенда),
  настройки темы/цветов/интервала
- Рендер оставить серверным (Pillow уже даёт пиксель-точный результат
  под панель); фронт только конфигурирует и показывает предпросмотр
- Учесть режим работы без панели (dev-режим: рендер в PNG)
- Целевой деплой: Linux/Proxmox (systemd-сервис), пользователь
  использует Dokploy/Docker на других проектах — контейнер с
  пробросом USB возможен, но проще начать с systemd

## Правила для кода

- Никогда не использовать символ em dash в ответах и генерируемых
  файлах/документах
- Версии пакетов для package.json/requirements сверять с реестром,
  не полагаться на память
- Комментарии и вывод скриптов в этом проекте — на русском
